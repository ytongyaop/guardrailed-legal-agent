# 架构设计

本文说明系统的分层结构、状态图路由、三层判定的数据流，以及"模型说什么、程序信什么"的核验机制。数字与能力口径同 [README](../README.md)，不重复展开。

## 分层

| 层 | 位置 | 职责 |
| --- | --- | --- |
| domain | `src/mla/domain` | 纯函数内核：规则判定（rules）、必备条款缺项（missing）、条款候选（clauses）、槽位与追问规则（slots、asking）、可溯源校验（verify）、越界判定（boundary）、清单组装（checklist）、数据模型（models）、策略常量（policy）、字段目录（field_catalog）。零 I/O、零模型依赖，相同输入必然相同输出 |
| ports | `src/mla/ports` | 接口定义：存储（repository）、生成（generation）、检索（retrieval）。只声明协议，不含实现 |
| adapters | `src/mla/adapters` | 接口实现：SQLite 持久化（persist）、正则抽取（extract）、模型抽取（extract_llm）、BM25 / 向量 / 混合检索（rag）、DeepSeek 调用（llm）、Word 与 PDF 解析（files）、语义向量（embedding） |
| graph | `src/mla/graph` | LangGraph 状态图：13 个固定节点、状态定义与条件路由 |
| services | `src/mla/services` | 用例编排：核对任务（tasks）、条款级审查（clause_review）、追问（asking）、问答循环（qa_agent）、Word 报告（report） |
| ui | `src/mla/ui` | Streamlit 界面（app） |

依赖方向单向：外层依赖内层，domain 不 import 任何 adapter。节点函数用闭包绑定依赖集合（`Deps` 实例不进 state），单元测试注入假实现即可离线跑全图；节点返回状态增量，不原地修改。

## 数据与存储

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 账号、企业、合同、任务、日志 | `data/mla.sqlite3`（SQLite，5 张表：users / enterprises / contracts / tasks / logs） | 运行时数据。一个账号绑定一个企业；企业 ID 为空的查询不得返回全库数据；任务删除为软删，日志留痕 |
| 法源、规则、触发器、必备条款规格、案例、回归集与留出集 | `data/` 下的 JSONL / YAML 文件 | 判定依据，随仓库分发，各有独立校验脚本把关结构一致性 |
| 语义向量缓存 | `data/index/` | 向量检索路径的本地缓存目录；BM25 路径不依赖它 |
| 密钥 | 环境变量或 `.streamlit/secrets.toml`（不入库） | 只读取、不落盘、不进数据库 |

## 状态图：13 个固定节点

路由写死在图的边上（`graph/build.py`），模型没有任何通道改变图结构或路由条件：

```
START → intake → extract → boundary
  boundary ── 越界 ────────→ refuse → END
           ── 问答模式 ────→ retrieve
           ── 核对模式 ────→ slots_check
  slots_check ── 缺阻断项且未超轮数上限 → ask → slots_check
              ── 事实齐全或已达轮数上限 → retrieve
  retrieve ── 问答模式 → qa_answer → verify
           ── 核对模式 → rule_check → checklist → verify
  verify ── 通过 → output → END
         ── 失败 → degrade → output → END
```

| 节点 | 职责 | 模型参与 |
| --- | --- | --- |
| intake | 入口，补齐状态默认值，防止下游拿到 None | 无 |
| extract | 合同关键字段抽取：正则优先、模型只补缺失字段，用户显式提供的事实优先覆盖；正文超过字数上限截断 | 可选 |
| boundary | 越界判定三层：劳动用工术语定向 → 检索兜底 → 都不命中则默认保守拒答 | 无 |
| slots_check | 阻断项与可补充事实是否齐全，纯代码 | 无 |
| ask | 生成追问并把轮数加一：程序定字段，模型只润色问句，八道核验不过逐条退回固定问句 | 可选 |
| retrieve | 法源检索：BM25 与向量混合（RRF 融合），已做时效过滤；无 Key 或断网回退纯 BM25 | 无 |
| rule_check | 20 条确定性规则判定，四态输出，违规条目自带规则 ID 与法条 ID | 无 |
| checklist | 汇总风险清单；生成处理建议（必须带依据，无模型则不生成）；旁路执行必备条款缺项检测 | 可选 |
| qa_answer | 受限问答：依据检索到的条文作答，无模型或无条文直接拒答 | 是 |
| verify | 可溯源校验：结论与建议的依据集合＝规则表法条与规则 ID ＋ 本轮检索命中 | 无 |
| refuse | 拒答并给转介建议，不产出任何结论 | 无 |
| degrade | 校验失败的降级出口：保留结论，标记"依据不足" | 无 |
| output | 结果落库，写日志（token、耗时） | 无 |

条款级审查（存在性域）不在图内：图跑完后由 `services/tasks.py` 统一编排执行，结果与规则结论一起落库。这样图的主干保持确定性，存在性域整体不可用时（无模型、开关关闭）不影响其余两层出结果。

## 三层判定的数据流

### 数值域（rule_check 节点）

抽取与用户输入合并成结构化事实 → 逐条规则先看前提（每条规则可带两组前提，`and` / `or` 决定组合关系）→ 前提适用的进入数值比较 → 输出四态：违规、合规、不适用、无法判定。"无法判定"再细分两类归因：缺前提字段，或前提已满足但判定字段缺失——两种都显式输出给用户，绝不折叠成"合规"。

### 存在性域（services/clause_review.py）

28 条触发器扫描合同正文，召回可疑条款候选，每个候选带段落号、原文片段与该触发器允许引用的法条闭集 → 候选分批送模型逐条判定 A/B/C 级，要求给出证据原文与法条引用 → 每条输出过六道程序核验（见下节）→ 通过的结论与规则结论按"规则判定 → A → B → C"混排。模型在候选之外自提的问题，条数封顶、一律记 C 级，不采信其自报等级。开关 `MLA_CLAUSE_REVIEW` 默认开启；模型调用失败或 JSON 非法时该层输出空结果加错误说明，不阻塞主流程。

### 缺项域（checklist 节点旁路，domain/missing.py）

按《劳动合同法》第十七条的九类必备条款规格逐行匹配合同正文，不跨行拼接；每类输出四态之一：已写、缺失、未见、需人工确认。只判"有没有写"，不判合法性——写了"自愿放弃缴纳社保"也算已写，其违法性归存在性域的触发器管。第（九）类为兜底规格，不判、不进覆盖率分母；正文过短时整体落"需人工确认"，不产生缺失结论。结果单独落库，不混入风险条目列表，避免污染数值域的评测口径。

## 为什么模型不能决定流程

流程即代码：哪个环节接哪个环节、什么条件拒答、什么条件补问、什么条件降级，全部写在状态图的边和路由函数里。模型的决策空间被压缩到三个点，且每个点都有程序兜底：

1. 问答循环内（services/qa_agent.py）：决定调什么工具、查几轮、何时停。工具只暴露"查法条 / 查规则"两个；工具失败或轮数用完，回退固定检索作答；收敛后的回答仍只接受工具已返回的来源。
2. 追问环节：从程序给定的字段闭集里挑可补充项、把问句润色得更自然。问什么、最多问几条、阻断项必须全覆盖，由程序决定。
3. 条款级判定：对触发器召回的候选给 A/B/C 等级、写证据与理由。引用不得越出候选法条闭集，等级要过核验。

这样做的收益是错误半径受限：抽取失败回退纯正则，条款审查失败该层置空，问答无模型就拒答。每个降级都显式标注并落库，系统不会把模型缺席伪装成正常结论；反过来，模型的发挥空间也永远出不去核验的包围圈。

## 模型输出的程序核验

### 条款判定：六道核验

1. 等级合法：只接受 A / B / C，其余直接丢弃。
2. 证据可定位：证据必须能在合同原文中找到位置，定位不到丢弃。
3. 法条在库：引用条号必须存在于 143 条法源库，库外引用丢弃。
4. 引用闭集：触发器候选的引用不得越出随候选下发的法条闭集，模型不得自由引法，越界丢弃。
5. 缺依据降级：A / B 级没有法条依据的，一律降为 C 级。
6. 位置采信候选：模型给的证据与候选片段重叠不足时，片段位置以候选为准。

前四道是硬性核验，不过即整条丢弃；后两道是软性处理，保留结论但降级或修正。每条丢弃与降级都写入诊断信息，随任务落库，可事后审计。评测脚本另设关闭核验的消融臂，用来度量"没有核验层模型会输出什么"，该臂只用于评测，不用于生产展示。

### 追问：八道核验

1. 字段闭集：只能挑本轮待补范围内的字段，越界丢弃。
2. 去重：同一字段只保留一条。
3. 条数上限：超上限按序截断。
4. 阻断项全覆盖：模型漏问的阻断项用固定问句补齐。
5. 问句形态：单行不含换行、字数在规定区间、以问号结尾。
6. 禁引法条编号：追问不向用户甩条号。
7. 禁结论性说法：追问不得预判核对结果。
8. 数值一致：问句里的数字必须来自已填事实或该字段的固定问句，其余视为编造。

任一条不过，只有该条退回固定问句，不牵连其他条目；模型调用整体失败时全部使用固定问句。追问环节永不抛异常。

### 可溯源校验（verify 节点）

每条结论与建议的 `source_id` 必须落在"规则表法条与规则 ID ＋ 本轮检索命中"的允许集合内，校验器按 100% 强制执行——这是输出的放行条件，不是目标值。建议类条目无依据则拒绝生成。任何一条说不清来源，整次结果走 degrade：结论保留但标记"依据不足"，错误清单随任务落库。

### 消融开关

核验与分层不只是设计说法，还做成了可拆装的开关，供评测逐层度量贡献：`MLA_EXTRACT_MODE` 控制抽取档（`regex` 档纯代码、离线可复现，测试固定用这一档），`MLA_CLAUSE_REVIEW` 控制存在性域整体启停，评测脚本另可按 `--variant` 拆臂（`rules_only` / `rules_retrieval` / `llm_only` / `full`，默认 `all` 连跑其中三臂）。条款级评测还设有关闭程序核验的模型裸输出臂。各臂指标与结果见 [evaluation.md](evaluation.md)。

### 隐私口径（与核验同级的设计约束）

追问只发送结构化事实与字段说明，问答只发送问题与本次核对的结构化摘要（事实、规则命中、条款段落号与等级、命中法条），两条路径都不发合同正文。合同正文仅在抽取环节发送给模型，界面有明确提示。
